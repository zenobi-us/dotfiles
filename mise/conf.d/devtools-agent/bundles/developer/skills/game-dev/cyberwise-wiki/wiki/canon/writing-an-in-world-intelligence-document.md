# Writing an in-world intelligence document that reads as real

A file about a person is the most convincing character document in this setting
and the easiest one to get subtly wrong. The failure is always the same: a story
wearing a file's clothes. Headings and a monospace font on top of ordinary
narration.

**What makes it read as real is that the document has an author with a job**, and
the six things below are all consequences of that.

## 1. Name the person once, then go cold

The header carries the name. After that the document says **SUBJECT**.

That single move does more than every other formatting decision combined. Real
files depersonalise, because the person is a case rather than a friend, and the
reader feels the institution's indifference without being told about it. A file
that keeps using the character's first name has already stopped being a file.

## 2. Hedge, source, and grade the source

Files do not assert. They **assess, and say how confident they are and where it
came from.**

```
ASSESSMENT: SUBJECT probably retained the contact after termination.
CONFIDENCE: Moderate.
SOURCE: Single reporting stream, previously reliable. Not corroborated.
```

**Grade source reliability explicitly.** A document that distinguishes a
corroborated claim from a single unverified stream is doing the thing real
intelligence products do - and it hands the reader a built-in way to be *wrong*
about the character, which is a gift.

The hedge vocabulary is small and worth using consistently: assessed, probably,
likely, possible, unconfirmed, not corroborated, single-source.

## 3. Write vulnerabilities as exploitation vectors, not character flaws

The difference is the whole tone of the document.

| a story says | a file says |
|---|---|
| "V drinks too much and misses their mother" | "SUBJECT maintains contact with one family member; leverage available. Alcohol use assessed as regular; judgement degradation under stress is unconfirmed." |

Same facts. But the second one is written by somebody deciding **what to do with
them**, and that is chilling in a way no amount of describing V's sadness would
be. The reader is put in the position of the institution, which is the most
Cyberpunk thing a document can do to them.

## 4. Give every quoted excerpt a one-line assessor's note

An excerpt on its own is just a quote. An excerpt with an analyst's comment
underneath it is a **document about a person, written by a second person**, and
the gap between what the subject said and what the assessor made of it is where
all the good work happens.

```
EXCERPT: "I did what they told me. That was the whole job."
NOTE: Deflection. SUBJECT has used this construction in two prior interviews.
```

One line. Not a paragraph - the assessor is busy.

## 5. Advised actions are numbered, assigned and postured

A file ends in **recommendations**, and real ones have three properties: they are
enumerated, they have an owner, and they carry a posture.

```
RECOMMENDED ACTIONS
1. Maintain passive monitoring. OWNER: Branch security. POSTURE: Non-attributable.
2. Do not approach. OWNER: All units. POSTURE: Standing.
```

The posture is what sells it. "Non-attributable", "standing", "on approval",
"pending review" - each implies a whole apparatus behind the page.

## 6. Leave quoted interviews verbatim

**This is the rule people break, and it is the one that costs the most.**

The instinct is to tidy a quoted interview so it reads well within the file. Do
not. Real files reproduce testimony unedited - the stumbles, the interruptions,
the sentence that goes nowhere. And the clash between a person's actual voice and
the file's clinical formality **is the entire effect.** Smoothing the quote
removes the only warmth in the document and leaves nothing for the coldness to
work against.

If the character swears mid-answer, the file contains the swearing. That is what
a transcript is.

## What to avoid

- **Do not invent institutional apparatus to fill the header.** Named
  departments, named systems, named directors and named projects read as canon to
  a reader and are the fastest way for a player's invention to be mistaken for
  the game's. If the game does not name it, either leave the field generic or put
  the player's name on the document.
- **Do not let the file be right about everything.** A document that has the
  character perfectly assessed is an omniscient narrator in a costume. Let it be
  confident and partly wrong; mark which parts are single-source, and let those
  be the wrong ones.
- **Do not use it for a character whose world would not have produced it** - see
  [Match the document format to the world](/canon/match-the-document-to-the-world).

## Scope

Craft. No patch dependency, no in-game source - this is how to make a fiction
read as a document, not a description of a document the game ships.
