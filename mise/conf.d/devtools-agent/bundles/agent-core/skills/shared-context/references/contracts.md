# Shared-context contracts

The installed `contracts.json` declares support. Run the shared skill-contracts router to validate declarations or resolve definitions. Shared-context validates domain content at owning operations. The definitions below are authoritative.

## Configuration

- `shared-context-routes/v2`: historical TOML with `schema = 2` and six `[records.<kind>]` tables: alignment, tickets, initiatives, workflows, evidence, sources. Each table has an adapter. Local tickets accept `markdown` or `local-markdown` and require a store. External ticket adapters have no store. Other stores are `repository` or `shared`; evidence also accepts `inherit:workflows`, and sources accepts `inherit:alignment`. Adapter identifiers use lowercase letters, digits, and hyphens. Unknown authored fields remain preserved.
- `shared-context-routes/v3`: the same interpretation, with `schemaVersion = "shared-context-routes/v3"` instead of `schema`. Both fields together are invalid.
- `shared-context-layout/v1`: historical TOML with `schema = 1` and optional `[paths]`. Only tracker and sources paths are supported. Paths are nonempty relative directories without traversal, empty components, backslashes, NUL, or drive prefixes.
- `shared-context-layout/v2`: the same interpretation, with `schemaVersion = "shared-context-layout/v2"` instead of `schema`. Both fields together are invalid.
- `shared-context-config/v1`: machine-local JSON with optional `schemaVersion` equal to this identifier and a nonempty string `storage_path`. Missing configuration uses the default without writing. Historical unversioned JSON uses the same rules. Unknown explicit identifiers fail. This reader never renames `storage_path`.
- `shared-context-project/v1`: stored project JSON with optional `schemaVersion` equal to this identifier and string `origin`. The canonical remote must match the store slug. Historical unversioned JSON remains readable. Unknown explicit identifiers fail. Identity recovery creates new versioned identities exclusively and preserves existing historical identity bytes. It does not change routes or source records.

## Source metadata and indexes

`shared-context-source/v1` describes Markdown source frontmatter. New or refreshed owned copies declare `schemaVersion: shared-context-source/v1` and use the provenance template in [Layout](layout.md). Supported legacy source copies have no identifier; inspection does not rewrite them. Optional source, title, and url fields are strings. The source identifier uses lowercase letters and hyphens. The body and all other fields belong to the source copy and remain unchanged. Externally owned explicit formats remain opaque: indexing reads title and URL, but never converts or relabels those documents. Explicit unknown shared-context identifiers fail.

`shared-context-index/v1` describes managed Markdown indexes. New frontmatter declares this schemaVersion, source, scope, generated_by equal to shared-context, and generated_at as an ISO timestamp. A managed block uses exactly one ordered pair of `<!-- shared-context:index start -->` and `<!-- shared-context:index end -->`. Historical unversioned managed blocks remain accepted. Index updates preserve all bytes outside that block, including authored frontmatter. Structured YAML parsing rejects duplicate keys. Explicit index metadata requires nonempty string source and scope, generated_by equal to shared-context, and a UTC ISO timestamp generated_at. Owned source metadata rejects non-string source, title, or url fields when present. Unknown explicit identifiers and ambiguous marker pairs fail before writes. Unmanaged authored indexes require the existing explicit --force replacement authority. Immutable events and artifacts are not index targets, including canonical targets reached through ancestor symlinks.

## Resolution

[Layout and location semantics](layout.md) remain authoritative for record paths, stores, references, and publication. `shared-context-resolution/v1` extends those retained rules with the following JSON shape and identifier. It is the JSON result of `resolve --json`. Required fields are schemaVersion, kind, adapter, store, root, path, ref, publication. kind names the requested record or collection. store is repository or shared. root and path are absolute; path stays in root after symlink resolution. ref is repository-relative or starts shared://. publication is repository or push-if-remote. Existing field names retain their meaning. The CLI rejects invalid input before producing a result. The XML session injection and external tracker/worktree formats keep their existing owner contracts.

## Conversion boundary

Read-only report, resolution, and index input inspection never upgrade configuration or source copies. `upgrade --artifacts <paths.json>` explicitly converts selected mutable route/layout configuration through skill-contracts. It reports per-item partial outcomes. This operation changes content versions, not storage routes. `configure-route --kind <kind> --store <store>` updates one route through the same safe upgrade layer; it does not copy files. Use storage migrate separately when files must move. Existing route migration preserves authored route text when updating its selected routing policy. Explicit shared policy takes precedence over explicit repository policy; both take precedence over legacy storage inference. Migration preflights the complete shared upgrade and requested mutation before copying records, then repeats the guarded upgrade at commit. Empty collections create shared identity metadata before the route commits.

Only route v2 to v3 and layout v1 to v2 have supported conversions. Source bodies, unmanaged indexes, machine configuration, project identities, receipt chains, and external formats have no bulk conversion. Unsupported paths, unsafe syntax, unknown explicit versions, and ambiguous identification fail without changing the rejected artifact.
